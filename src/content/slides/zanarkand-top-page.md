# トップページを<br />WebGL で作り直した話

スクロールを「見る順番を設計する入力」に変えた

---

## 何を作ったか

静的なポートフォリオを、スクロールで都市を進むWebGLページに置き換えた

- 既存の文章構成は残し、読ませる順番だけをカメラワークに割り当てた
- three.jsのシーンは、各セクションの文脈を変える背景として使った
- WebGLが動かない環境、低速端末、`prefers-reduced-motion` では通常の縦積みページに戻す
- 目的は、プロフィールを最後まで読んでもらう導線を作ること

---

## 作る前の課題

トップページは情報が多いほど、読み手の視線が途中で切れる

- プロフィール、制作物、文章、現在地が同じ重さで並び、どこから読めばよいか分かりにくかった
- 作品画像だけを大きくしても、エンジニアとしての文脈までは伝わりにくかった
- SPA的な派手さを足すと、静的サイトの軽さやアクセシビリティを壊しやすい
- そこで「文章は静的、見せ方だけ動的」という制約を先に置いた

---

## 設計方針

WebGLは、読み手を次の章へ運ぶ舞台として扱う

| 方針 | 意味 |
| --- | --- |
| 文章を先に成立させる | Canvasが消えても内容が読める |
| スクロールを入力にする | ユーザーの操作感をブラウザ標準に寄せる |
| カメラで章を切る | セクション移動に意味を持たせる |
| フォールバックを同時に作る | 低速端末で壊れた印象を残さない |

---

## 実装構成

Astroは静的な骨格を持ち、three.jsはその上に重ねるだけにした

```text
src/
├── pages/index.astro          # マークアップ（5章ぶん）
├── components/home/
│   ├── CityStage.astro        # canvas とフォールバック
│   └── city/
│       ├── config.ts          # カメラの経由点
│       └── scene.ts           # three.js 本体
├── scripts/home-city.ts       # スクロール → 進捗 → カメラ
└── styles/home-city.css       # 夜のパレット
```

---

## レイヤーを分ける

DOM、Canvas、スクロール状態を混ぜないことで、壊れた時の調査範囲を狭めた

<div class="diagram">
  <div class="node">Astro<small>本文とリンク</small></div>
  <div class="arrow">→</div>
  <div class="node">Scroll State<small>0..1の進捗</small></div>
  <div class="arrow">→</div>
  <div class="node">three.js<small>カメラと復元演出</small></div>
  <div class="arrow">→</div>
  <div class="node">CSS<small>パネルと余白</small></div>
</div>

- HTMLは検索、OGP、キーボード操作に耐える通常のページとして残す
- three.js側は「進捗を受け取り、現在の見え方を描く」責務だけにする
- CSSはCanvasの上に置くパネルの可読性を担い、シーンの都合を持ち込まない

---

## カメラは経由点だけ書く

カメラを直接制御せず、通ってほしい視点を少数の点として定義した

```ts
export const WAYPOINTS: Waypoint[] = [
  { pos: [360.0, 178, 0.0], target: [0, 46, 0] },   // 海の上から俯瞰
  { pos: [-20.4, 55, -62.8], target: [0, 46, 0] },  // 球体へ寄る
  { pos: [0.0, 52, 0.0], target: [0, 52, 0] },      // 水中を通過
]
```

Catmull-Romで補間し、スクロール進捗 `0..1` を曲線上の位置に割り当てる

---

## カメラ設計で効いた判断

カメラの自由度を絞るほど、スクロール体験は破綻しにくくなる

| 判断 | 効いた理由 |
| --- | --- |
| 経由点を少数にする | 調整箇所が減り、視点移動の意図が説明できる |
| targetも補間する | 視線だけが急に飛ぶ違和感を避けられる |
| 章ごとに意味を持たせる | 「寄る」「潜る」「見上げる」がセクションの内容と結びつく |
| 手動操作を入れすぎない | ポートフォリオ閲覧の主目的から外れない |

---

## スクロールを自前で持つ

ドキュメント全体を動かさず、専用スクローラから距離だけを受け取った

- ページ本体は固定し、スクロール量を `progress` に変換する
- カメラ、復元演出、セクション表示は同じ `progress` を参照する
- ブラウザの戻る、リンク、フォールバックとの衝突を減らすため、DOM構造はできるだけ普通に保つ
- 実装上は便利でも、スクロールイベントに処理を詰め込みすぎないようにした

---

## シーンは章に合わせて進む

都市が組み上がる進捗を、プロフィールを読む進捗と同期させた

<div class="timeline">
  <div class="step"><strong>Intro</strong><span>遠景から世界観を見せる</span></div>
  <div class="step"><strong>Profile</strong><span>中央の構造物へ寄る</span></div>
  <div class="step"><strong>Works</strong><span>街のディテールを増やす</span></div>
  <div class="step"><strong>Writing</strong><span>視線を落ち着かせて本文を読ませる</span></div>
</div>

- 見た目の変化をセクション内容に同期させると、スクロールに理由が生まれる
- 動きが大きい章と小さい章を分け、全編が同じテンションにならないようにした
- テキストが読みにくい場面では、演出より背景の暗さと静けさを優先した

---

## ハマったところ

継承していた文字色が、パネルを `<body>` へ移した瞬間に消える

```css
/* .city の外に出た時点でこれは効かなくなる */
.city { color: var(--city-ink); }

/* 色はパネル自身に持たせる */
.city-panels { color: var(--city-ink); }
```

> 位置を動かす最適化は、継承も一緒に動かす。

---

## CSSで壊れやすい場所

WebGLページのバグは、Canvasより重なり順と継承で起きやすい

| 症状 | 原因 | 対応 |
| --- | --- | --- |
| パネルの文字が消える | 親要素から外れてCSS変数を失う | パネル自身に色変数を持たせる |
| クリックできない | Canvasや透明レイヤーが前にいる | `pointer-events` と z-index を分ける |
| スクロールが二重になる | bodyと専用スクローラが同時に動く | 入力経路を1つにする |
| モバイルで読めない | Canvas基準の余白が小さい | 文章側のレスポンシブを先に作る |

---

## パフォーマンス

重いものを軽くするより、重い処理を動かさない条件を先に作った

| 項目 | 方針 | 理由 |
| --- | --- | --- |
| モデル | Draco圧縮のGLBを1つだけ | 読み込み数を増やさない |
| 描画 | `prefers-reduced-motion` で静的版に切替 | 動きが不要な環境を尊重する |
| 初期表示 | シーン読み込み前は背景で代替 | 真っ白な待ち時間を作らない |
| DPR | 上限2でクランプ | 高解像度端末でGPU負荷を膨らませない |
| 監視 | FPS低下時は演出を控える | 完璧な絵より読めるページを優先する |

---

## フォールバック

フォールバックは、最初から同じ情報を届ける別ルートである

- Canvasが初期化できない場合でも、本文セクションは通常のページとして読める
- 画像やモデルに依存しない見出し、リンク、プロフィール導線を残す
- reduced motionでは、読みに集中できる版にする
- フォールバックを先に作ると、WebGL側が失敗しても開発中の確認が止まらない

---

## 実装で見た指標

雰囲気だけでは改善できないので、最低限の観測点を決めた

<div class="metric-grid">
  <div class="metric"><strong>LCP</strong><span>最初に意味のある画面が出るまで</span></div>
  <div class="metric"><strong>FPS</strong><span>スクロール中に体感が落ちないか</span></div>
  <div class="metric"><strong>Readability</strong><span>各パネルの文字が背景に負けていないか</span></div>
</div>

- スコアだけを追うと、体験の悪い軽量化に寄りやすい
- スクロール中の読みやすさは、パフォーマンスと同じくらい重要だった
- スクリーンショットで各章の見え方を確認し、背景と文字の衝突を潰した

---

## 次に直すなら

運用しながら直せる構造にしておくことが大事だった

- セクション追加時にWAYPOINTSを手で調整する負荷を下げる
- モバイルでは3Dの密度を落とし、文章の余白を優先する
- シーンの状態と本文の章番号をより明示的に紐付ける
- 視覚確認をPlaywrightのスクリーンショットで自動化する

---

## まとめ

WebGLを入れるなら、動きの前に「読める構造」を守る必要がある

- スクロールに意味を与えると、同じ文章でも読み方が変わる
- three.jsは独立した舞台にし、本文とリンクは通常のHTMLとして残す
- 退避は速いが、CSSの継承とクリック範囲は必ず壊れやすくなる
- フォールバックを先に書くと、派手な演出を足してもページの芯が残る
