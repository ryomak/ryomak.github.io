# はじめてのEMが知るべきチーム運営の基礎

EMの仕事は、個人の頑張りをチームの再現性に変えることである

---

## EMの役割

EMはメンバーの力が成果につながる仕組みを作る人である

- 目標を分かる形にする
- 詰まりを早く見つける
- 役割と期待値をそろえる
- 学習と採用でチームの上限を上げる

---

## チームの状態を見る

最初に見るべきは、チームの雰囲気より仕事の流れである

- 何が入口になり、何が完了条件か
- 誰がどこで待っているか
- レビュー、仕様確認、意思決定の滞留はどこか
- 失敗が起きた時に個人名で語られていないか

---

## 最初に見ないもの

初任EMは、見やすい問題から直すほど本筋を外しやすい

| 見たくなるもの | なぜ危ないか | 先に見るもの |
| --- | --- | --- |
| 個人の頑張り | 根性論に寄りやすい | 待ち時間、手戻り、依存関係 |
| 会議の数 | 減らすだけでは意思決定が詰まる | 会議ごとの判断内容 |
| ベロシティ | 数字だけ上げると品質が落ちる | リリースまでの流れ |
| 不満の声 | 大きい声だけ拾いやすい | 事実、影響、頻度 |

- 最初の観察で個人評価を始めると、メンバーは問題を隠す
- チームの詰まりを、個人の能力不足として扱わないことが信頼の出発点になる

---

## 期待値をそろえる

期待値が曖昧なチームでは、善意の努力が衝突する

- チームの優先順位を3つ以内に絞る
- 役割ごとの責任範囲を言語化する
- 「よい仕事」の基準をレビューで共有する
- やらないことも明文化する

---

## 期待値の表

期待値は、役割、成果、行動、境界の4つで書くとずれにくい

| 項目 | 書くこと | 例 |
| --- | --- | --- |
| 役割 | 何を担うか | API設計の主担当 |
| 成果 | 何が出ればよいか | 決済導線を安全に出す |
| 行動 | どう進めるか | 早めにレビューを出す |
| 境界 | 何を抱えないか | 仕様判断はPdMと決める |

---

## 1on1の使い方

1on1では、相談を受けながら認識ずれも早期に見つける

- 仕事の詰まり
- 期待値とのずれ
- 成長機会
- チームやプロダクトへの違和感

---

## 1on1でやらないこと

1on1を進捗確認の場にすると、本当に必要な相談が出てこなくなる

| やりがちなこと | 何が失われるか | 置き換え |
| --- | --- | --- |
| チケット確認だけで終わる | 本人の詰まりや不安が出ない | 進捗は非同期、1on1は背景を聞く |
| EMが解決策を即答する | 本人の判断機会が減る | 選択肢と判断基準を一緒に作る |
| 雑談だけで終わる | 期待値のずれが残る | 最後に次の行動を1つ決める |
| 評価面談化する | 防御的な会話になる | 評価の話は時期と目的を分ける |

- 1on1の成果は話した量より、次の仕事の進め方が少し明確になること
- 毎回完璧にするより、違和感が小さいうちに拾える場として続ける

---

## 1on1の問い

よい問いは、気合いより事実を引き出す

| 観点 | 質問 |
| --- | --- |
| 詰まり | 今週、最も時間を使っている待ちは何か |
| 期待値 | 何を優先すべきか迷っていることはあるか |
| 成長 | 次に任されたい仕事は何か |
| チーム | 言いにくいが直したほうがよいことは何か |

---

## 会議を減らす前に設計する

会議の数より、意思決定の置き場所を先に決める

| 会議 | 目的 |
| --- | --- |
| Daily | 進捗報告より詰まりの検知 |
| Planning | 何を捨てるかを決める |
| Retrospective | 再発防止より次の実験を決める |
| 1on1 | 認識ずれを早く見つける |

## 評価と育成

育成は、本人の努力と次の仕事の設計をつなぐことで進む

- 期待値を行動で説明する
- 次の挑戦を少しだけ難しくする
- フィードバックは事実、影響、期待の順で伝える
- 評価直前に初めて伝える話をなくす

---

## 成長機会を設計する

育成は研修を足すだけでなく、次の仕事の難易度を調整することで進む

| 状態 | 任せる仕事 | EMの支援 |
| --- | --- | --- |
| 初めての領域 | 調査と小さな実装 | 背景、制約、レビュー観点を渡す |
| 慣れてきた領域 | 設計と関係者調整 | 判断基準だけ先に合わせる |
| 得意領域 | 成果責任を持つ単位 | 途中介入を減らし、事後で学びを整理 |
| 次の役割候補 | 他者を助ける仕事 | フィードバックと期待値の言語化を支援 |

- 「任せる」は作業量より、判断範囲を渡すこと
- 難しすぎる仕事は放置になり、簡単すぎる仕事は成長機会にならない
- 本人の希望とチームの必要を重ねる場所を探す

---

## コンフリクト

衝突は、未解決の前提が表に出ている状態である

- 何を守りたい衝突かを分解する
- 技術論、期限、品質、責任範囲を混ぜない
- 当事者だけで抱えさせない
- 最後は判断基準をチームの資産にする

---

## EMが最初にやること

最初の30日は、変えるより先に地図を作る

- チームの仕事の流れを書く
- 主要な意思決定者を把握する
- メンバー全員と期待値を確認する
- 1つだけ小さな滞留を解消する

---

## まとめ

チームを前に進めるEMは、個人の頑張りを進み方の設計に変える

- 目標を絞る
- 流れを見る
- 期待値を合わせる
- 学習できる仕組みにする

---

## 40分の構成

初任EM向けには、理論より「明日から見る場所」を揃える

| 時間 | パート | 持ち帰るもの |
| --- | --- | --- |
| 0-7分 | EMの役割 | 何に責任を持つか |
| 7-17分 | チームの流れ | 詰まりの見つけ方 |
| 17-27分 | 期待値と会話 | 1on1、委譲、フィードバック |
| 27-35分 | 意思決定 | 会議、責任範囲、コンフリクト |
| 35-40分 | 30日計画 | 最初にやること |

## EMの責任範囲

EMは、成果が出るチームシステムを設計する人である

  <div><h4>People</h4><p>期待値、成長機会、フィードバックを設計する。</p></div>
  <div><h4>Quality</h4><p>障害、レビュー、技術的負債が成果を壊さないようにする。</p></div>

## 委譲の段階

任せる時は、判断範囲を明確にする

| 段階 | メンバーの権限 | EMの関わり |
| --- | --- | --- |
| 観察 | 調査して提案する | 背景と制約を説明 |
| 推奨 | 選択肢を比較して勧める | 判断基準を確認 |
| 実行 | 決めた範囲で進める | 途中でリスクを見る |
| 所有 | 成果と改善を持つ | 事後レビューに回る |

---

## 意思決定の型

迷いが長いチームは、決め方が決まっていない

| 型 | 向いている場面 | 注意点 |
| --- | --- | --- |
| Owner decides | 責任者が明確 | 事前に相談範囲を示す |
| DACI | 関係者が多い | Driverを一人にする |
| RFC | 技術判断 | 期限を切る |
| Experiment | 不確実性が高い | 成功条件を先に置く |

---

## ステークホルダー管理

EMはチーム内と外側の期待値をそろえる必要がある

| 相手 | そろえること |
| --- | --- |
| PdM | 優先順位、スコープ、リリース条件 |
| Design | 仕様の未確定部分、レビュータイミング |
| SRE / Platform | 運用負荷、セキュリティ、依存関係 |
| 経営 | 目標、採用、技術負債への投資判断 |

- チームが遅いように見える時、実際には外部判断待ちで止まっていることがある
- EMは全てを代わりに決める人ではない。決めるべき人に、決められる情報を届ける人である
- 外側との認識ずれを放置すると、メンバーへの期待値も曖昧になる

---

## 悪い状態の早期サイン

大きな問題になる前に、会話とフローに小さな変化が出る

| サイン | 起きている可能性 |
| --- | --- |
| レビュー依頼が遅い | 完成まで見せにくい心理、粒度の大きさ |
| 仕様確認がDMに閉じる | 判断が共有知になっていない |
| 障害後に個人名が出る | 仕組みで直す文化が弱い |
| 会議後に別の合意が生まれる | 会議で決める人と場がずれている |
| 強い人に仕事が集まる | 委譲と育成が止まっている |

<div class="quote-panel">EMの仕事は、悪化の前兆をチームで扱える形にすること。</div>

## フィードバックの構造

性格に踏み込まず、事実と影響と次の行動を扱う

<div class="case">

## 30/60/90日プラン

最初の3か月は、信頼、流れ、改善サイクルを順に作る

| 期間 | 目的 | やること |
| --- | --- | --- |
| 30日 | 地図を作る | 1on1、業務フロー、KPI確認 |
| 60日 | 小さく直す | 滞留1つ、会議1つ、期待値1つ |
| 90日 | 再現性を作る | 目標設計、育成計画、意思決定ルール |

## 運営リズム

会議は、情報の流れを整える装置である

| 頻度 | 場 | 扱うこと |
| --- | --- | --- |
| 毎日 | Daily | 詰まり、依存、今日捨てること |
| 毎週 | Planning/Review | 優先順位、完了、学び |
| 隔週 | Retrospective | 次の小さな実験 |
| 毎月 | Growth sync | 期待値、成長機会、役割 |
